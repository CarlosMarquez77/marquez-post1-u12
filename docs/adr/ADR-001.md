# ADR-001: Capas simples para la persistencia; la notificación ya tiene su punto de extensión

## Estado
Aceptado — 2026-10-10

## Contexto
El sistema de solicitudes de reembolso ya integra Chain of
Responsibility (validación), Strategy (cálculo) y Observer
(notificación). Falta decidir si el proyecto completo debe pasar a
arquitectura Hexagonal, con puertos para todas sus dependencias
externas, o quedarse en capas simples.

Datos del proyecto que pesan en la decisión:

- La persistencia se usa desde una sola clase,
  `SolicitudReembolsoService`, y con tres operaciones
  (`findByEmpleadoIdAndEstado`, `findById` y `save`).
- Las reglas de negocio están en `procesamiento`, que no depende de
  JPA ni de Spring Data, y sus pruebas unitarias corren sin base de
  datos ni contexto de Spring.
- El modelo de dominio tampoco importa JPA: el mapeo de
  `SolicitudReembolso` está en `META-INF/orm.xml`.
- No existe ningún plan de cambiar el motor de base de datos.
- Contabilidad anunció para el próximo trimestre una integración por
  API externa para el pago de las solicitudes aprobadas.

La guía de la unidad (sección 6.2) da el criterio: la arquitectura
Hexagonal vale la pena en sistemas que sobrevivirán tres años o más
con cambios de infraestructura.

## Alternativas consideradas
1. **Hexagonal completa.** Puertos para persistencia y notificación,
   con sus adaptadores. Aísla todo, pero agrega una interfaz, un
   adaptador y un mapper de persistencia para un cambio que nadie ha
   pedido.
2. **Puerto solo para la persistencia.** Una interfaz
   `RepositorioSolicitudes` con un adaptador JPA. Es menos costosa que
   la anterior, pero el beneficio principal de un puerto, probar las
   reglas sin base de datos, ya se tiene porque las reglas no están en
   el servicio.
3. **Capas simples.** El servicio depende directamente de
   `RepositorioSolicitudesJpa`. No agrega nada.

## Decisión
Se decide mantener capas simples para la persistencia:
`SolicitudReembolsoService` sigue dependiendo de
`RepositorioSolicitudesJpa`, sin una interfaz intermedia. El criterio
de la guía no se cumple para la persistencia: no hay ningún cambio de
infraestructura previsto, así que el puerto sería una abstracción
especulativa (YAGNI) con un solo implementador.

Para la notificación no se introduce ningún cambio. El criterio sí se
cumple ahí, porque hay un cambio de infraestructura con fecha, pero el
punto de extensión ya existe: `ObservadorCambioEstado`. La integración
de Contabilidad se resuelve cambiando el cuerpo de
`NotificadorContabilidad` o agregando otro observador, sin tocar el
servicio ni los demás notificadores.

## Consecuencias
Positivas:
- No se agregan interfaces, adaptadores ni mappers de persistencia sin
  un caso de uso que los pida.
- El único cambio de infraestructura con fecha conocida ya tiene dónde
  conectarse.
- La decisión se puede revertir a bajo costo: el repositorio se usa en
  una sola clase y con tres métodos.

Negativas:
- Si algún día se cambia el motor de base de datos, el puerto habrá
  que introducirlo después. Se acepta esa deuda de forma consciente.
- `SolicitudReembolsoService` solo se puede probar levantando Spring y
  H2, con pruebas de integración más lentas que las unitarias.
- Los observadores se ejecutan uno tras otro dentro de
  `cambiarEstado`. Cuando `NotificadorContabilidad` llame a una API
  externa, una falla o una demora de esa API afectará la petición y a
  los observadores que sigan en la lista. Hoy no es un problema porque
  los tres solo escriben en consola o en el log.
- Quien espere simetría (puertos en todas las dependencias externas)
  puede leer la diferencia como una inconsistencia si no conoce este
  ADR.

## Cuándo revisar esta decisión
- Aparece un requisito real de cambiar o agregar un motor de
  persistencia.
- El servicio de aplicación empieza a tener reglas propias que
  convenga probar sin base de datos.
- Se implementa la integración con la API de Contabilidad: en ese
  momento hay que decidir si la notificación debe ser asíncrona.
